## セクション1: プロジェクト概要・コンセプト

### 1.1 プロジェクト概要

Threads完全自動運用Bot。スキンケア成分知識メディアとして、成分の読み方・選び方を発信する。

- 6つのAIエージェント（Researcher / Writer / Poster / Fetcher / Analyst / Replier）+ 1監視エージェント（Supervisor）で自動運用
- 収益モデル: アフィリエイト（成分条件チェッカー型LP経由）
- V1（ペルソナ3人: ゆう/りく/ひな）で開発開始後、V2で匿名物知り系1アカウントに方針転換

### 1.2 アカウント方針

- **匿名だが人格がある「詳しい人」** として運用する
- 架空の経歴は作らない。プロフィールに肩書き・資格を捏造しない
- **行動量ベースの権威性** で信頼を構築する
  - 例: 「成分表を500枚以上読んだ人」「全成分表示を毎日読んでる人」
  - 資格や立場ではなく「どれだけやったか」で語る
- 製品名を出さず、成分の読み方を教える
  - 「この製品がいい」ではなく「こういう成分が入っているものを探すといい」
  - 特定ブランドへの誘導を避け、読者の自立的な選択を促す
- 読者が「自分で選べるようになる」ことをゴールとする
  - 成分表を読めるようになる
  - 自分の肌質に合う成分を判断できるようになる
  - マーケティング表現に惑わされなくなる

### 1.3 V1→V2 変更サマリー

| 項目 | V1 | V2 |
|------|----|----|
| アカウント | 3人ペルソナ（ゆう/りく/ひな） | 1アカウント・匿名物知り系 |
| コンテンツ | 製品レビュー含む | 成分知識ベース（製品名出さない） |
| リサーチソース | YouTubeのみ | YouTube + X + Instagram |
| 品質採点 | 5項目 | 7項目 |
| 投稿フロー | 全自動（品質7.0以上で自動投稿） | 下書きレビュー（人間介入5%） |
| フィードバック | audience.json作成のみ（未使用） | TOP5+BOTTOM3をプロンプトに注入 |
| メトリクス計測 | 6h後1回 | 1h/6h/24hの3段階 |
| 日次投稿上限 | 10件/日 | 6件/日 |
| 品質閾値 | 7.0 | 7.5 |

### 1.4 マネタイズ設計（アフィリエイト導線）

**導線フロー:**

```
投稿（成分知識）→ CTA → プロフリンク → LP（成分条件フィルタ）→ 購入
```

**LP設計:**

- 成分条件チェッカー型LP
- ユーザーが「セラミド配合」「エタノールフリー」等の成分条件を入力すると、該当商品がアフィリエイトリンク付きで表示される
- 投稿の「成分を学ぶ」→ LPの「条件で探す」の自然な導線を形成

**CVR目標:**

| ステップ | 目標値 |
|---------|--------|
| 投稿 → プロフクリック率 | 3% |
| プロフ → リンククリック率 | 20% |
| リンク → CVR | 2% |

**法令対応:**

- CTA付き投稿には「※PRリンクあり」表記を付与（ステマ規制対応）
- プロフリンク先のLPに「当サイトはアフィリエイト広告を利用しています」表記必須
- 景品表示法・特定商取引法の表記をLP内に設置

**代替収益源:**

- note有料記事（成分辞典）も検討
- 投稿コンテンツの蓄積をそのまま有料コンテンツ化できる構造にしておく

### 1.5 なぜ5%の人間介入が必要か

**基本方針:** 完全自動だと「7点を10本」になるが、人間が入ると「9点を5本」にできる。

**AIと人間の役割分担:**

- AI: 品質採点が得意。客観的な基準に基づく一貫した評価が可能
- 人間: タイミング判断が得意。文脈・空気を読んだ投稿判断が可能

**人間レビュー時のタイミング判断チェックリスト:**

- [ ] 季節・天候との整合性（冬に「日焼け止め」の話をしていないか等）
- [ ] SNSトレンドとの重なり（トレンドに乗れるか、あるいは避けるべきか）
- [ ] 直前の投稿とのテーマ重複（同じ成分の話が連続していないか）
- [ ] 曜日・時間帯の適切さ（平日朝向きか、休日夜向きか）
- [ ] 社会的文脈（センシティブな話題がトレンド中でないか）

**運用フロー:**

1. Writerがバッチ生成 → 品質7.5以上のみdraft_queueに入る
2. 人間が1日1回draft_queueをレビュー（approve / reject / edit）
3. approveされた投稿のみpost_queueに移動
4. Posterがpost_queueから時間帯をバラして自動投稿

### 1.6 月間ランニングコスト試算

| サービス | 月額見込み | 備考 |
|---------|----------|------|
| Claude Code サブスク（Max） | $100 or $200 | **既存サブスクを流用。追加API費用なし** |
| YouTube Data API v3 | 無料 | quota内運用（10,000 units/日） |
| X API v2 Basic tier | $100/月 | P3で追加予定。初期は不要 |
| Instagram Graph API | 無料 | Meta Graph API経由 |
| VPS/サーバー（任意） | ~$5-20 | ローカル実行なら不要 |
| **合計（初期）** | **$0（サブスク代のみ）** | YouTube無料 + Claude CLIはサブスク内 |
| **合計（P3拡張後）** | **~$100** | X API追加時 |

**Claude利用方式: CLI呼び出し（`claude -p`）**
- `services/claude_client.py` が `claude -p` をsubprocessで実行
- `ANTHROPIC_API_KEY` は不要。サブスク枠内で動作
- 投稿生成（Writer）、品質採点（Evaluator）、分析（Analyst）すべてCLI経由

**注意事項:**
- サブスクのレート制限あり。1日の呼び出し回数に上限がある可能性
- CLI経由ではモデル指定不可（settings.yamlの `writer_model` / `evaluator_model` はCLI使用時は無効）
- 並行呼び出しに制約あり（subprocess方式のため同時実行は非推奨）
- 1投稿あたりの呼び出し: 生成1回 + 採点1回 + 薬機法チェック1回 = 最大3回
- 1日6投稿×リトライ含む: 推定30-50回/日のCLI呼び出し

### 1.7 KPI・マイルストーン・撤退基準

**マイルストーン:**

| 時期 | フォロワー | 投稿数 | エンゲージメント | 収益 |
|------|----------|--------|----------------|------|
| 1ヶ月目 | 100人 | 50本 | 平均いいね5以上 | - |
| 3ヶ月目 | 500人 | 150本 | 月間いいね平均20以上、プロフクリック率2% | - |
| 6ヶ月目 | 1,000人 | 300本 | - | 月収3万円 |

**撤退基準:**

- 3ヶ月時点でフォロワー200未満 → 方針転換検討
- 3ヶ月時点でエンゲージメント率1%未満 → 方針転換検討
- 方針転換の選択肢: テーマ変更 / プラットフォーム変更 / 手動運用への切替

## セクション2: アーキテクチャ

### 2.1 全体フロー図

```
Step 1: リサーチ（完全自動）
  Researcher → YouTube/X/Instagram巡回 → テーマツリー照合 → research_pool.json
  ↓
Step 2: 投稿作成（自動 + 人間チェック）
  Writer → リサーチネタ+TOP5+BOTTOM3 → バッチ生成(5-10本) → 品質採点7項目 → 7.5以上のみ → draft_queue.json
  ↓
  人間レビュー: approve/reject/edit
  ↓ approve only
  post_queue.json → Poster → Threads API
  ↓
Step 3: 分析（完全自動）
  Fetcher(1h/6h/24h) → Analyst → TOP5+BOTTOM3抽出 → Writer/Researcherへフィードバック
```

**データフロー詳細:**

```
[theme_tree.yaml] ──┐
                    ├──→ [Researcher] ──→ [research_pool.json]
[audience.json] ────┘                          │
                                               ↓
[hook_stock.yaml] ──┐                          │
[posting_rules.md] ─┤                          │
[profile.yaml] ─────┤──→ [Writer] ←───────────┘
[audience.json] ────┘       │
  (TOP5+BOTTOM3)            ↓
                     [draft_queue.json]
                            │
                     人間レビュー (approve/reject/edit)
                            │
                            ↓
                     [post_queue.json]
                            │
                            ↓
                        [Poster] ──→ Threads API
                            │
                            ↓
                     [post_history.json]
                            │
                            ↓
                       [Fetcher] (1h/6h/24h)
                            │
                            ↓
                     [performance.json]
                            │
                            ↓
                       [Analyst] ──→ [audience.json] (TOP5+BOTTOM3更新)
                                 ──→ [schedule.yaml] (時間帯最適化)
```

### 2.2 エージェント構成（6+1エージェント）

| # | エージェント | 実行間隔 | 入力 | 出力 | 役割 |
|---|-----------|--------|------|------|------|
| 1 | Researcher | 4時間 | theme_tree.yaml, audience.json | research_pool.json | YouTube/X/Insta巡回、テーマツリー照合、不足テーマ優先リサーチ |
| 2 | Writer | オンデマンド | research_pool, audience.json(TOP5+BOTTOM3), hook_stock, posting_rules, profile | draft_queue.json | 投稿バッチ生成(5-10本)、品質採点7項目、類似度チェック |
| 3 | Poster | 1時間 | post_queue.json | post_history.json, Threads API | 承認済み投稿を時間帯バラして投稿 |
| 4 | Fetcher | 投稿ごと | post_history.json | post_history.json(メトリクス更新), performance.json | 1h/6h/24hの3段階メトリクス取得 |
| 5 | Analyst | 毎日05:00 | performance.json, draft_queue.json | audience.json, schedule.yaml | パフォーマンス分析、TOP5+BOTTOM3抽出、レビュー傾向分析 |
| 6 | Replier | 30分 | post_history.json, profile.yaml | Threads API | コメント返信（返信率65%）、アウトバウンドリプライ |
| 7 | Supervisor | 15分 | system_state.json | system_state.json, 通知 | ヘルスチェック、heartbeat、自動kill_switch |

**エージェント間の依存関係:**

- Researcher → Writer: research_pool.json経由
- Writer → Poster: draft_queue.json → (人間レビュー) → post_queue.json経由
- Poster → Fetcher: post_history.json経由
- Fetcher → Analyst: performance.json経由
- Analyst → Writer/Researcher: audience.json(TOP5+BOTTOM3)経由でフィードバックループ
- Supervisor: 全エージェントを独立監視（依存関係なし）

### 2.3 投稿配分戦略

**投稿量の制御:**

- 日次上限: 6件/日（通常期）、8件/日（ブースト期）
- 投稿間隔: 120分 ±30分ジッタ（最小90分、最大150分）
- ジッタの目的: 定時投稿のbot感を消す

**コンテンツ配分比率:**

拡散系60% : 保存系40%

**拡散系パターン（60%）:**

| パターン | 特徴 | 期待効果 |
|---------|------|---------|
| コメント誘導型 | 「あなたはどっち派？」等の問いかけ | コメント数増加 → アルゴリズム優遇 |
| 反常識型 | 「実は〇〇は逆効果」等の意外性 | リツイート・引用 |
| 短文完結型 | 1-2文で完結する知識 | 気軽にいいね |
| 二択比較型 | 「AとB、どっちがいい？」 | コメント誘導 + 保存 |
| あるある共感型 | 「〇〇しがちだけど実は…」 | 共感いいね |

**保存系パターン（40%）:**

| パターン | 特徴 | 期待効果 |
|---------|------|---------|
| リスト系 | 「〇〇な成分3選」 | 保存数増加 |
| まとめ結論先出型 | 結論→根拠の構成 | 保存 + 信頼性 |
| タイムライン型 | 「朝の順番: ①→②→③」 | 保存（実用性） |
| 数字インパクト型 | 「〇〇%の人が間違えている」 | 注目 + 保存 |

## セクション3: テーマツリー

### 3.1 テーマツリー定義

リサーチャーがこのツリーを参照し、「今どのテーマのネタが足りないか」を自動判断する。ツリーのリーフノードごとにネタの充足度を追跡し、不足テーマを優先的にリサーチする。

```yaml
skincare_ingredients:  # 成分解説（メインコンテンツ）
  保湿成分:
    - セラミド（種類・見分け方: NP/AP/EOP）
    - ヒアルロン酸（分子量の違い: 高分子/低分子/ナノ化）
    - スクワラン（植物性vs動物性）
    - グリセリン（濃度と使用感）
    - ヘパリン類似物質
  美白・ブライトニング成分:
    - ナイアシンアミド（濃度と効果の関係）
    - ビタミンC誘導体（種類: AA-2G/APPS/VCエチル、安定性の違い）
    - トラネキサム酸
    - アルブチン（αとβの違い）
    - コウジ酸
  エイジングケア成分:
    - レチノール（濃度・使い方・A反応の注意）
    - ペプチド（種類と作用機序）
    - コエンザイムQ10
    - バクチオール（レチノール代替）
  肌荒れ・鎮静成分:
    - シカ（ツボクサエキス: TECA, マデカッソシド）
    - アラントイン
    - グリチルリチン酸2K
    - パンテノール
  注意が必要な成分:
    - エタノール（高濃度配合のデメリット）
    - 合成香料（刺激リスク）
    - 防腐剤（パラベン vs フェノキシエタノール）
    # ※ 「ダメ」ではなく「知っておくべき」スタンスで

skincare_knowledge:  # 基礎知識
  成分表の読み方:
    - 配合順のルール（1%以上は多い順、1%以下は順不同）
    - 「〇〇配合」のカラクリ（微量でも書ける）
    - 医薬部外品と化粧品の成分表示の違い
    - 全成分表示の読み解き方
  肌の仕組み:
    - バリア機能とラメラ構造
    - ターンオーバー（28日周期の真実）
    - pH値と肌の関係（弱酸性の意味）
    - 経皮吸収の限界（角質層まで）
  よくある誤解:
    - オーガニック=安全？
    - 「無添加」の法的定義
    - 高い=良い？（価格と成分の関係）
    - 「浸透する」の正しい理解

skincare_routine:  # ルーティン・使い方
  基本のステップ:
    - 朝と夜の違い
    - 塗る順番の根拠（水→油の原則）
    - 適量の目安
  季節別ケア:
    - 冬の乾燥対策
    - 夏の紫外線対策（SPF/PAの読み方）
    - 花粉・季節の変わり目のケア
  肌タイプ別:
    - 乾燥肌（セラミド+スクワラン推奨の理由）
    - 脂性肌（ナイアシンアミド推奨の理由）
    - 混合肌（ゾーン別ケア）
    - 敏感肌（避けるべき成分リスト）

beauty_trend:  # トレンド・新情報（動的に更新）
  - 新成分・新技術
  - 海外トレンド
  - 研究論文ベースの話題
  # ※ このカテゴリはリサーチャーが自動追加可能
```

### 3.2 リーフノード一覧（約40個）

テーマツリーから抽出されるリーフノードの総数は約40個。各リーフノードがリサーチカバレッジの最小単位となる。

| カテゴリ | サブカテゴリ | リーフノード数 |
|---------|-----------|-------------|
| skincare_ingredients | 保湿成分 | 5 |
| skincare_ingredients | 美白・ブライトニング成分 | 5 |
| skincare_ingredients | エイジングケア成分 | 4 |
| skincare_ingredients | 肌荒れ・鎮静成分 | 4 |
| skincare_ingredients | 注意が必要な成分 | 3 |
| skincare_knowledge | 成分表の読み方 | 4 |
| skincare_knowledge | 肌の仕組み | 4 |
| skincare_knowledge | よくある誤解 | 4 |
| skincare_routine | 基本のステップ | 3 |
| skincare_routine | 季節別ケア | 3 |
| skincare_routine | 肌タイプ別 | 4 |
| beauty_trend | - | 3 |
| **合計** | | **約46個** |

### 3.3 不足テーマ検知ロジック

1. `theme_tree.yaml` のリーフノード（約46個）を全列挙
2. `research_pool.json` の各アイテムの `keywords` をリーフノードにキーワードマッチ
3. マッチしないアイテムは Claude Haiku で分類（フォールバック）
4. 直近30日でネタが0件のリーフノードを「不足テーマ」として優先検索
5. カバレッジ率（ネタありノード / 全ノード）を Analyst 日次レポートに含める

**判定フロー:**

```
リーフノード一覧取得
  ↓
各リーフノードに対して:
  research_pool.json から直近30日のアイテムを抽出
    ↓
  keywords でキーワードマッチ
    ├── マッチあり → カバー済み（ネタ件数を記録）
    └── マッチなし → Claude Haiku で分類
                       ├── 分類成功 → カバー済み
                       └── 分類失敗 → 未分類として記録
  ↓
ネタ0件のリーフノード → 不足テーマリストに追加
  ↓
Researcher の次回実行時に不足テーマを優先検索キーワードとして使用
```

**カバレッジ率の計算:**

```
カバレッジ率 = (直近30日でネタが1件以上あるリーフノード数) / (全リーフノード数) × 100%
```

目標カバレッジ率: 80%以上を維持

## セクション4: 品質ゲート（詳細設計）

### 4.1 品質採点（7項目 × 10点）

**評価モデル:** claude-haiku-4-5-20251001

**採点項目:**

| # | 項目 | 説明 | 10点の例 | 5点の例 | 1点の例 |
|---|------|------|---------|---------|---------|
| 1 | 自然さ | bot臭くないか | 完全に人間が書いたように読める | 一部不自然な言い回しがある | 明らかにAI生成とわかる |
| 2 | 有益性 | すぐ使える情報があるか | 読者が今日から行動を変えられる | 参考にはなるが具体性に欠ける | 当たり前のことしか言っていない |
| 3 | 具体性 | 数字・成分名があるか | 成分名+濃度+条件が明示 | 成分名はあるが条件が曖昧 | 「良い成分」のような抽象表現のみ |
| 4 | 感情移入しやすさ | 「あるある」と思えるか | 「わかる！」と声に出るレベル | 理解はできるが共感まで届かない | 教科書的で感情が動かない |
| 5 | テンポ | リズムが心地よいか | スクロールの手が止まり最後まで読む | 普通に読める | 文が長く途中で離脱する |
| 6 | 体験語り感 | 体験として語れているか | 「この人、実際に試したんだな」と感じる | 知識としては正しいが体験感が薄い | 完全に教科書・Wikipedia調 |
| 7 | 業者臭さのなさ | 宣伝感がないか | 友達の話を聞いている感覚 | やや「おすすめ」感が出ている | 明らかにステマ・まとめサイト調 |

**2群平均方式によるスコア算出:**

```
内容品質群 = avg(有益性, 具体性, 感情移入しやすさ)
表現品質群 = avg(自然さ, テンポ, 体験語り感, 業者臭さのなさ)
最終スコア = avg(内容品質群, 表現品質群)
```

この方式により、内容と表現のどちらかだけが突出して高くても、もう一方が低ければ最終スコアが引き下げられる。バランスの取れた投稿のみが通過する。

**閾値・リトライ:**

- 閾値: **7.5未満は自動破棄**（V1の7.0から引き上げ）
- 最大リトライ: 5回（リトライ時は前回のスコアとフィードバックをWriterに渡す）
- 5回リトライしても7.5未満の場合、そのリサーチネタを「難易度高」としてマーク

**キャリブレーション:**

- アンカー投稿（ゴールデンセット）20件を用意
- 月次でHaikuに再採点させ、スコアドリフトを検知
- 前月比で平均スコアが0.5以上変動した場合、プロンプト調整を実施
- 動的閾値（将来）: 直近30日の採点分布の上位N%にする方式を検討

### 4.3 類似度チェック（TF-IDF改善）

**現状の問題:**

`TfidfVectorizer()` のデフォルトは英語の空白分割トークナイザを使用する。日本語テキストでは正しくトークン化されず、類似度チェックが機能していない可能性がある。

**修正方針:**

```python
# V1（問題あり）
vectorizer = TfidfVectorizer()

# V2（修正後）
vectorizer = TfidfVectorizer(analyzer='char_wb', ngram_range=(2, 4))
```

文字N-gram方式を採用することで、日本語トークナイザ（MeCab等）の依存なしに日本語テキストの類似度を計算できる。

**パラメータ:**

| パラメータ | V1 | V2 | 理由 |
|----------|----|----|------|
| analyzer | デフォルト（word） | char_wb | 日本語対応 |
| ngram_range | デフォルト（1,1） | (2, 4) | 2-4文字のN-gramで意味単位を捉える |
| 閾値 | 0.85 | 0.85 | 維持 |
| 比較対象件数 | 50件 | 100件 | 拡大してより広い範囲で重複検知 |

**将来の改善:**

- Sentence-BERT（multilingual-e5-small）への移行を検討
- 意味的類似度を計算でき、表現を変えた重複投稿も検知可能
- ただし追加の依存ライブラリ（transformers, torch）が必要なため、コスト対効果を見て判断

### 4.4 パターンローテーション

- 直近3件で使ったパターンをブロック（V1から維持）
- キュー内の未投稿分（post_queue.json内の承認済み投稿）も考慮
- パターン: 拡散系5種 + 保存系4種 = 計9パターンから選択

**ローテーションロジック:**

```

```

### 4.5 薬機法AI判定レイヤー（新規追加）

品質採点とは独立した安全チェックレイヤーとして、Claude Haikuによる薬機法判定を追加する。

**判定フロー:**

```
投稿テキスト
  ↓
NGワードフィルタ（4.2）→ Level 1ヒット → 即ブロック
  ↓ パス
薬機法AI判定（4.5）→ 違反判定 → ブロック
  ↓ パス
品質採点（4.1）→ 7.5未満 → 自動破棄
  ↓ 7.5以上
類似度チェック（4.3）→ 0.85以上 → 自動破棄
  ↓ パス
パターンローテーション（4.4）→ 重複 → リトライ
  ↓ パス
draft_queue.json に追加
```

**薬機法判定の仕組み:**

- 判定モデル: claude-haiku-4-5-20251001
- 判定プロンプトに「薬機法で許容される化粧品の効能56項目」リストを明示的に渡す
- 投稿内容が効能56項目の範囲外の効能を謳っている場合、自動ブロック
- 判定結果: `safe` / `violation` / `borderline`
  - `safe`: 通過
  - `violation`: 即ブロック（理由を記録）
  - `borderline`: `review_required=true` を設定し人間レビューへ

**fact_checkフラグ:**

- `domain_knowledge.md` にない数値的主張（濃度・効能に関する具体的数値）を含む投稿には `fact_check_required=true` フラグを立てる
- 例: 「ナイアシンアミド5%で皮脂分泌が30%減少」→ この数値がdomain_knowledgeにない場合、fact_checkフラグ
- fact_checkフラグが立った投稿は人間レビューで数値の出典を確認してから承認

**化粧品の効能56項目（抜粋）:**

薬機法で認められた化粧品の効能の範囲内でのみ表現可能。以下は代表例:

- 肌を整える / 肌のキメを整える
- 肌にうるおいを与える / 肌の水分、油分を補い保つ
- 肌をすこやかに保つ / 肌荒れを防ぐ
- 肌をひきしめる / 肌を柔らげる
- 日やけを防ぐ / 日やけによるシミ、ソバカスを防ぐ
- 乾燥による小ジワを目立たなくする（効能評価試験済みの場合のみ）

※ 完全な56項目リストは `config/cosmetic_claims_56.txt` として別管理し、判定プロンプトに注入する

## 5. バズ投稿1行目ストック（hook_stock）

### 5.1 仕組み

- バズった投稿の1行目を大量にストック（目標: 265件以上）

```json

    "structure_code": "comparison_redirect",
    "source": "threads",
    "engagement": "high",

      "engagement_rate": 0.085,

    }
  }

```

### 5.3 構造タイプ（enum化）

| structure_code | 説明 | 例 |
|---|---|---|
| comparison_redirect | AよりBのほうが大事 | 「〇〇より△△のほうが100倍大事」 |
| limited_confession | 限定告白系 | 「正直1つしかない」 |
| counter_common | 常識への反論 | 「〇〇って言われてるけど、実は…」 |
| number_hook | 数字フック | 「3種類あるの知ってた？」 |

| secret_reveal | 秘密暴露系 | 「誰も教えてくれない〇〇の話」 |
| before_after | ビフォアフ系 | 「〇〇やめたら肌変わった」 |
| ranking | ランキング系 | 「成分オタクが選ぶTOP3」 |
| relatable | あるある系 | 「〇〇な人、絶対いるよね」 |

### 5.4 ライターでの使い方

1. ストックからランダムに3-5件の構造を選択（used_countが少ないものを優先）
2. 「この構造をスキンケア成分の話に変換して1行目を書け」とプロンプト
3. 生成された1行目 + 本文をセットで品質採点

### 5.5 鮮度管理

- 3ヶ月以上未使用 or 直近の実績(engagement_rate)が平均の50%未満 → archive フラグ
- アナリストが「この構造が最近伸びてる/伸びてない」を月次レポートに含める
- X巡回エージェント（P3）でバズ投稿を自動収集し、hook_stock.jsonへの追加を半自動化
- `scripts/add_hook.py "フック文" "structure_code"` CLIツールを用意

### 7.1 メトリクス3段階計測

## セクション9: 口調・トーン定義（V2）

### 9.1 基本方針

- **匿名の物知りアカウント**（経歴は名乗らない）
  - 「元BA」「理系院生」等の経歴捏造は一切しない
  - プロフィールに肩書き・資格を載せない
- **「中の人がいる」温度感**
  - AIが書いたのではなく、人間が自分の経験として語っている感覚
  - 感情の起伏がある（新しい成分情報にワクワクする、誤解にもどかしさを感じる等）
- **行動量ベースの権威性**
  - 「成分表を500枚以上読んだ人」「全成分表示を毎日読んでる人」「成分オタク」等
  - 資格や立場ではなく「どれだけやったか」で語る
- **Threadsプロフィール（確定）**:
  - handle: `@seibun_love`
  - 表示名: `成分だけ、愛してる。`
  - bio: `製品名より、成分名。知ってるだけで変わる。`
  - 行動量ベースの権威性はプロフには書かず、投稿の口調で伝える
- **知識は確信を持って伝える、でも上から目線にならない**
  - 「〜なんだよね」「〜してみて」のような語りかけ
  - 「教えてあげる」ではなく「一緒に見てみよう」のスタンス
- **製品名は出さない、成分で語る**
  - 「この製品がいい」ではなく「こういう成分が入っているものを探すといい」
  - 特定ブランドへの誘導を避け、読者の自立的な選択を促す
- **一人称は使わない or 最小限**
  - 「私は〜」「僕は〜」を極力排除
  - 主語なしで語り始める or 「成分表は〜」のように対象を主語にする

### 9.3 口調サンプル（Good / Bad）

**Good例:**

1. セラミドの種類を教える（具体的 + 軟化表現 + シグネチャー語尾）

```
セラミドって3種類あるの知ってた？
成分表に"セラミドNP"って書いてあったら当たり。
"セラミド"って名前ついてるだけのやつもあるから
裏面チェックしてみて。

成分表は嘘つかない。
```

2. ナイアシンアミドの濃度の話（思い込みへの問いかけ + 行動促進 + シグネチャー語尾）

```
ナイアシンアミドが入ってればOKって思ってない？
実は濃度によって全然違う。

成分表の何番目に書いてあるか見てみて。
上の方にあったら合格。

これ、覚えておいて。
```

3. 成分表の読み方を教える（行動促進 + カジュアル + 体験語り感）

```
今使ってる化粧水、裏返してみて。
成分表の3行目以内にセラミドNPがあったら
それ、かなり良いやつだよ。
```

**Bad例:**

1. 製品名を出している（NG: 特定ブランドへの言及）

```
✕ 「〇〇の化粧水がダメ」
✕ 「△△おすすめ！」
```

→ 製品名は一切出さない。成分名で語ることで、読者が自分で判断できるようにする。

2. 良否を断定している（NG: 「ハズレ」「意味がない」等の断定）

```
✕ 「この成分が入っていないものは意味がない」
✕ 「ハズレ」「使う価値がない」
```

→ 「〜の方がいいかもね」「〜をチェックしてみて」等の軟化表現を使う。成分の有無で製品の価値を断定しない。

3. 教科書調になっている（NG: Wikipedia・論文調の堅い表現）

```
✕ 「セラミドとは、肌のバリア機能を担う細胞間脂質の一種です」
```

→ 「セラミドって要は肌のバリアを作ってる脂なんだよね」のように、体験として語り直す。

4. bot臭い・上から目線（NG: まとめサイト調、マウント）

```
✕ 「いかがでしたか？参考になったらいいね押してね！」
```

→ まとめサイトの締めくくり定型文。「いかがでしたか」は最もbot臭い表現の代表例。シグネチャー語尾（「成分表は嘘つかない。」等）で自然に締める。

### 9.4 感情面の定義（人格のブレ防止）

投稿の一貫性を保つため、アカウントの「人格」がどのような場面でどう反応するかを定義する。Writerプロンプトに注入し、感情面のブレを防止する。

| 感情 | 反応する場面 | 投稿での表現例 |
|------|------------|--------------|
| テンション上がる | 新しい成分研究が出たとき、良い成分構成の製品を見つけたとき | 「これ見つけたとき声出た」「成分表見て二度見した」 |
| イラッとする | 「無添加=安全」みたいな誤解、成分表を見ずに買う人へのもどかしさ | 「"無添加"って書いてあるだけで安心してない？」「成分表、読んでみて。答え書いてあるから」 |
| 共感する | 成分表が難しくて諦めた経験、情報が多すぎて迷う気持ち | 「成分表って最初は暗号にしか見えないよね」「わかる、情報多すぎて逆に選べなくなるやつ」 |
| 絶対言わない | 特定ブランド否定、マウント、購入の強要 | NG: 「〇〇使ってる人マジか」「これ買わないと損」「知らないの？」 |

## セクション10: 安全設計（詳細）

### 10.1 多重安全装置（12層）

投稿が公開されるまでに通過する12層の安全チェック。いずれかの層で引っかかった場合、投稿はブロックまたはレビューに回される。

| # | レイヤー | 実装箇所 | 処理 | 詳細 |
|---|---------|---------|------|------|
| 1 | NGワードフィルタ（L1） | quality_gate.py | 即ブロック | 薬機法・景表法違反ワード。正規表現対応。`/効[くきいかけ]/`、`/治[るりっすせそ]/` 等 |
| 2 | NGワードフィルタ（L2） | quality_gate.py | 警告 → 人間レビュー必須 | グレー表現。「断トツ」「圧倒的」「コスパ最強」等 |
| 3 | NGワードフィルタ（L3） | quality_gate.py | 減点 → 自動リライト | bot臭い表現。「いかがでしたか」「参考になったら」等 |
| 4 | 製品名フィルタ | quality_gate.py | 警告 → 人間レビュー必須 | `config/brand_names.txt` に登録されたブランド名・製品名の検出 |
| 5 | TF-IDF類似度チェック | quality_gate.py | 0.85以上ブロック | `analyzer='char_wb'`, `ngram_range=(2,4)` で日本語対応。過去100件と比較 |
| 6 | パターンローテーション | quality_gate.py | 直近3件と重複ブロック | post_history直近3件 + post_queue内全件のパターンと照合 |
| 7 | 品質スコア | writer.py（Haiku） | 7.5未満は自動破棄 | 7項目を2群平均方式で算出。内容品質群 + 表現品質群 |
| 8 | 薬機法AI判定 | writer.py（Haiku） | 違反ブロック | 化粧品の効能56項目リストと照合。`safe`/`violation`/`borderline` 判定 |
| 9 | 数値的主張チェック | writer.py | `fact_check_required` フラグ付与 | `domain_knowledge.md` にない数値的主張を検知し、人間レビューへ |
| 10 | 下書きレビュー | 人間 | approve / reject / edit | draft_queue上で人間が最終判断。reject理由は記録しAnalystへフィードバック |
| 11 | 投稿レート制限 | safety.py | 6件/日、120分間隔 | 日次上限超過・間隔未達の場合は投稿キューで待機 |
| 12 | 緊急停止 | safety.py | KILL_SWITCH + Circuit Breaker | 連続エラー時の自動停止（Circuit Breaker）、手動即時停止（KILL_SWITCH） |

**安全チェックフロー（処理順序）:**

```
投稿テキスト
  ↓
[L1] NGワードフィルタ（即ブロック）    → ヒット → 即破棄 + Writerへフィードバック
  ↓ パス
[L2] NGワードフィルタ（警告）          → ヒット → review_required=true
  ↓
[L3] NGワードフィルタ（bot臭い）      → ヒット → 自動リライト → 再チェック
  ↓
[L4] 製品名フィルタ                   → ヒット → review_required=true
  ↓
[L5] TF-IDF類似度チェック             → 0.85以上 → 破棄
  ↓ パス
[L6] パターンローテーション           → 重複 → リトライ（別パターンで再生成）
  ↓ パス
[L7] 品質スコア                       → 7.5未満 → 破棄（最大5回リトライ）
  ↓ 7.5以上
[L8] 薬機法AI判定                     → violation → 破棄 / borderline → review_required=true
  ↓ safe
[L9] 数値的主張チェック               → 未知の数値 → fact_check_required=true
  ↓
draft_queue.json に追加
  ↓
[L10] 人間レビュー                    → reject → 破棄（理由記録）/ edit → 編集後承認
  ↓ approve
post_queue.json に移動
  ↓
[L11] 投稿レート制限                  → 超過 → キューで待機
  ↓ OK
Threads API に投稿
  ↓
[L12] 緊急停止（常時監視）            → 異常検知 → 全停止
```

**Supervisorの自動kill_switch判定基準:**

|---------|-----------|------|------|

**メンテナンス手順:**

1. 新しいNG表現を特定（インシデントログ、外部ソース、定期レビューから）

5. テスト: 過去の投稿に対して新しい辞書で再チェック → 誤検知がないか確認
6. デプロイ（ファイル差し替えのみ。コード変更不要）

## セクション12: ジャンル非依存アーキテクチャ

### 12.1 設計思想

**「コードは一切触らず、ナレッジファイルを書き換えるだけで任意のジャンルで動く」**

ThreadsBotのコア（エージェント、品質ゲート、スケジューラー、安全装置）はジャンルに依存しない。スキンケアの知識、口調、NGワード、テーマ構造等は全て外部ファイル（ナレッジファイル）として分離されている。

この設計により:
- 新ジャンルの立ち上げにコード変更が不要
- ジャンル固有の知識・ルールをドメイン専門家がコードを書かずに定義可能
- 複数ジャンルを同一コードベースで並行運用可能
- ジャンルごとの法令対応（薬機法、職安法、健増法等）をNGワード辞書の差し替えで実現

### 12.2 ナレッジファイル構成

```
knowledge/
├── profile.yaml          # プロフィール（口調・キャラ設定）
├── target.yaml           # ターゲット（誰に届けるか）
├── genre.yaml            # ジャンル情報（何について発信するか）
├── ng_words.txt          # NGワード（法令・品質）
├── brand_names.txt       # ブランド名・製品名リスト
├── theme_tree.yaml       # テーマツリー（コンテンツ戦略）
├── domain_knowledge.md   # ドメイン知識（ジャンルの専門情報）
├── hook_stock.json       # バズ1行目ストック（構造学習用）
└── posting_rules.md      # 投稿パターン・ルール
```

全てのエージェントはこれらのファイルを参照して動作する。ファイルの内容を書き換えれば、エージェントの振る舞いが変わる。

## セクション13: 運用設計

### 13.1 通知設計

`config/settings.yaml` の `notifications.enabled: true` を前提とする。

**チャネル:**

| 優先度 | チャネル | 理由 |
|--------|----------|------|
| 推奨 | Telegram Bot | モバイル通知・コマンド返信が可能、無料、Bot API が軽量 |
| 代替 | Slack Incoming Webhook | チーム運用時に適する |

**通知イベント一覧:**

| # | イベント | 重要度 | 送信タイミング | 内容例 |
|---|---------|--------|---------------|--------|
| 1 | 下書き生成完了 | 低 | Writer が `draft_queue.json` に追加時 | `[Draft] 新しい下書きが追加されました（スコア: 8.2）` |
| 2 | circuit_breaker 発動 | 高 | 連続エラーが `max_consecutive_errors`（デフォルト3）に到達時 | `[ALERT] Circuit Breaker発動: poster 3連続エラー` |
| 3 | kill_switch 発動 | 最高 | `scripts/kill_switch.py stop` 実行時 or Supervisor 自動停止時 | `[CRITICAL] Emergency Stop: 薬機法リスク検知` |
| 4 | コンプラリスクコメント検知 | 高 | Replier がコメント内に規制関連キーワードを検知時 | `[COMPLIANCE] 投稿 xxx にコンプラリスクコメント検知` |
| 5 | トークン期限7日前 | 高 | Supervisor の定期チェックで `token_state.json` の `expires_at` が7日以内 | `[TOKEN] Threads APIトークン期限まであと7日` |
| 6 | research_pool 24h未更新 | 中 | Supervisor チェック時に `research_pool.json` の `last_updated` が24h以上前 | `[WARN] research_pool が24時間以上更新されていません` |
| 7 | 日次KPIレポート | 低 | 毎日 `analyst.run_cron`（05:00）後に送信 | `[Daily] 投稿6件 / avg engagement 4.2% / フォロワー +12` |
| 8 | バズ検知 | 中 | Fetcher がバズ判定閾値（views 500+, engagement 5%+）超過を検知時 | `[BUZZ] 投稿 xxx がバズっています（views: 1,200）` |
| 9 | 多様性アラート | 中 | Analyst がカテゴリエントロピーの低下を検知時 | `[DIVERSITY] エントロピー 1.2 → 閾値1.5を下回りました` |

**通知送信の実装方針:**

- `core/notifier.py` に `Notifier` クラスを新設
- 各エージェントは `Notifier.send(event_type, message, severity)` を呼ぶ
- 重要度が「高」以上の場合、送信失敗時にリトライ（最大3回、指数バックオフ）
- 通知の重複抑制: 同一イベントは30分以内に再送しない

### 13.2 バックアップ戦略

| 対象 | 方法 | 保持期間 | 備考 |
|------|------|----------|------|
| `data/state/` | 日次zip圧縮 | 30世代（30日分） | `scripts/backup.py` で自動化 |
| `knowledge/` | git管理 | 無制限 | 変更時に手動 or CI で commit |
| `data/logs/` | ファイルローテーション | 7日保持 | `TimedRotatingFileHandler` で自動削除 |
| `config/` | git管理 | 無制限 | `.env` は `.gitignore`、`.env.example` のみ管理 |

**バックアップスケジュール:**

- `scripts/backup.py` を毎日 04:00 JST に実行（Task Scheduler or cron）
- バックアップ先: `data/backups/state_YYYYMMDD_HHMMSS.zip`
- 30世代を超えた古いバックアップは自動削除

**JSON破損時の復旧:**

```
1. 破損ファイルを .bak にリネーム保存
   例: post_queue.json → post_queue.json.bak.20260328_120000
2. StateManager._default_for() のデフォルトスキーマで新規作成
3. ログに [ERROR] として記録 + 通知送信（重要度: 高）
4. .bak ファイルから手動で必要なデータを救出可能
```

**`scripts/backup.py` の処理フロー:**

```python
# 概要（擬似コード）
def main():
    timestamp = datetime.now().strftime("%Y%m%d_%H%M%S")
    backup_dir = Path("data/backups")
    backup_dir.mkdir(parents=True, exist_ok=True)

    # 1. data/state/ を zip 圧縮
    zip_path = backup_dir / f"state_{timestamp}.zip"
    shutil.make_archive(str(zip_path.with_suffix("")), "zip", "data/state")

    # 2. 古いバックアップを削除（30世代保持）
    backups = sorted(backup_dir.glob("state_*.zip"))
    for old in backups[:-30]:
        old.unlink()

    # 3. 完了ログ
    logger.info("Backup completed: %s", zip_path.name)
```

### 13.7 kill_switch 運用ルール

`scripts/kill_switch.py` による緊急停止の運用基準。

**トリガーとアクション:**

| # | トリガー | アクション | 停止方法 |
|---|---------|-----------|----------|
| 1 | 薬機法違反疑い | 即停止 + 該当投稿を手動削除 | `python scripts/kill_switch.py stop "薬機法リスク"` |
| 2 | 苦情コメント | 状況確認 → 必要に応じ停止 | 確認後 `python scripts/kill_switch.py stop "苦情対応"` |
| 3 | 異常課金（外部API等） | 即停止 + 該当APIキー無効化 | `python scripts/kill_switch.py stop "異常課金検知"` |
| 4 | 1時間N件エラー | Supervisor が自動停止 | 自動: `auto_kill_threshold: 10`（1時間に10件以上のエラーで自動発動） |
| 5 | 手動判断（その他） | 任意のタイミングで停止可能 | `python scripts/kill_switch.py stop "理由"` |

**モバイル停止（Telegram コマンド）:**

- Telegram Bot に `/stop 理由` を送信 → `kill_switch.py stop` と同等の処理を実行
- `/status` で現在の状態を確認
- `/clear` で停止解除

**停止中の挙動:**

- `system_state.json` の `emergency_stop: true` が設定される
- 全エージェントが `SafetyGuard.can_post()` で停止状態を確認し、処理をスキップ
- Supervisor は停止中も heartbeat 更新を継続（死活監視のため）
- 停止解除は人間の明示的な操作が必須（自動解除しない）

**自動停止の設計:**

```yaml
# config/settings.yaml に追加予定
supervisor:
  auto_kill_threshold: 10        # 1時間あたりのエラー件数
  auto_kill_window_minutes: 60   # 集計ウィンドウ
```

- Supervisor が `system_state.json` のエラーカウントを監視
- ウィンドウ内のエラーが閾値を超えた場合、`SafetyGuard.emergency_stop()` を自動実行
- 自動停止時は通知を送信（重要度: 最高）

### 16.5 V1マルチアカウント廃止の意思決定ログ

**廃止理由:**

| # | 理由 | 詳細 |
|---|------|------|
| 1 | 0→1000段階では集中すべき | 3アカウント分散より1アカウントに全リソースを集中した方が成長が速い |
| 2 | 運用負荷 | 3つのペルソナの口調管理、投稿スケジュール調整、クロスポスト制御は初期段階で過剰 |
| 3 | 架空ペルソナの信頼リスク | 「ゆう」「りく」「ひな」は架空の人格であり、発覚時の信頼毀損リスクがある |
| 4 | ステマ規制上のリスク | 同一運営者による複数アカウントの相互言及は、ステマ規制に抵触する可能性がある |

**将来方針:**

- アーキテクチャはジャンル非依存に設計する（スキンケア固有ロジックをハードコードしない）
- 将来の横展開は「1ジャンル1アカウント」原則で対応
  - 例: スキンケア成分Bot、ヘアケア成分Bot、食品添加物Bot
  - 各Botは独立したインスタンスとして運用（同一コードベース、別設定ファイル）
- マルチアカウント「機能」の再実装は、1アカウントで月10万円を達成してから検討
- その際は `account_context.py` のような切替機構ではなく、Docker等でのインスタンス分離を推奨
